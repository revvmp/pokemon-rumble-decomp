# ScriptWorldObj final helpers

## F-251-2: comparator construction and duplicate type predicate

The last three function gaps were the 48-byte `tree_begin_holder<less<int>>` constructor, its unnamed four-byte callee at `0x8014E130`, and the second 68-byte `IsKindOf<CPii, BWorldObj>` body. The complete source object initially matched 237/240 functions.

The four-byte callee is the empty `std::less<int>` default constructor. A unit-local specialization of `less<int>` supplies that constructor and preserves the original integer comparison operator. Defining it under a scoped `dont_inline on` pragma retains the call in the tree holder, matching both bodies. This avoids the regressions in other units documented for a project-wide comparator change in [sprint-a03](sprint-a03.md) and [sprint-a05](sprint-a05.md). The target symbol at `0x8014E130` is now `__ct__Q23std7less<i>Fv`.

The target contains a local predicate at `0x8014CF80` called by `DynamicCast<CPii>`, and another predicate at `0x8014D8F0` called by the direct script type query. The source previously emitted only one. A local `IsPiiForDynamicCast` predicate and a unit-local inline specialization of `DynamicCast<CPii, BWorldObj>` retain the first independent body. The helper tests exactly the same null condition and type bit as the template; the generic direct-query body remains unchanged. The earlier local target symbol is named for this helper, retaining local scope. The second symbol retains its template name.

Both changes are D-0016 fake matches. The compiler and source-organization differences that originally created the two predicate copies are not reconstructed. The comparator specialization is likewise a local code-generation accommodation, not a claim about the original standard-library header.

Direct Wii/1.1 compilation with the unit's generated flags and diagnostic symbol-table renames gives 240/240 functions at 100%. No shared header changed. The first coordinated Matching trial linked successfully but failed full SHA verification; the unit remains NonMatching pending function/data emission ordering. The 240 matching functions form a 224-function common ordered subsequence with the reference, so individual function identity alone is insufficient.

## Traps

A constructor-specific `__declspec(noinline)` was rejected by this compiler. A scoped `dont_inline on` around the local specialization retains the empty constructor and its call without changing shared headers. The duplicate type predicate must have independent source identity; changing static linkage on the existing template alone cannot create both copies.

## F-251-3: ordering experiments and native partial-link limit

A source-only scratch candidate moves ten static helper definitions after their first relevant callers, retaining forward declarations. This preserves all 240 individual function matches and improves the common ordered subsequence from 224 to 234. An unused, correctly typed pointer to `CBSPTree::Node::CalcDistance`, declared after the `Scale` call inside `method_moveTo`, makes the compiler emit `CalcDistance` before `KeepOutOfWall` without changing any function bytes. That D-0016 address probe improves the common sequence to 235/240. Neither the definition moves nor the probe is retained in the current source because source linking is still unverified. The complete candidate is preserved in `tools/local/session/282-worldobj/order-best.cpp`.

The remaining order problems are the allocator/tree-root constructor pair, the mutable list allocator/size accessor pair, the tree comparator and begin-holder accessor, and the set-iterator/bool pair constructor. Local specializations, earlier declarations with later definitions, and moving generic comparator bodies out of class do not fix them. Turning IPA off preserves all 240 function bodies but worsens the common sequence to 138; the `defer_codegen` pragma alone does not change the order under the configured IPA option.

A separate toy investigated ordinary compiler/linker sections and partial links, using only newly compiled C++ inputs. Native function section declarations work. The linker accepts section inputs but rejected attempted symbol-name input ordering. A template instantiated after a code-section pragma enters that section even if its template definition precedes the pragma. An `extern template` free-function declaration suppresses emission, but equivalent class/member declarations did not suppress the member in the bounded Wii/1.1 toy, including with ISO templates enabled.

The NXP [Power Architecture Build Tools Reference](https://www.nxp.com/docs/en/reference-manual/PA_Build_RM.pdf), pages 216 and 373, documents native partial-link exclusion and custom code sections. `EXCLUDEFILES` under an optimized partial link successfully removed a selected weak function from a genuine compiler object, kept its call relocation undefined, and did not copy the dummy selector function into the result. However, this linker rejects the optimized partial result as input to every subsequent tested native link mode. Plain partial linking ignores the exclusion. Therefore the selector pipeline is not a usable reconstruction route under the native-only constraints and is not integrated. No object-header edits, byte patches, original-object selectors or assembly regeneration were used to bypass that rejection.

The bounded reproductions are `tools/local/session/282-linkorder.py`, `282-linksection.py`, `282-partial.py` and `282-partial-join.py`. They are tooling diagnostics, not source-coverage evidence. The rejected intermediate also generated constructor/destructor terminators, reinforcing the need to validate an entire native pipeline before adopting partial linking.

## F-251-4: native source fragments reproduce the complete function sequence

A five-fragment scratch prototype now reproduces all 240 function bodies and their complete target order. It uses the ordinary Wii/1.1 compiler and a plain `mwldeppc -nodefaults -fp hardware -r` join. Every input contains newly compiled typed C++ source. No target object is a linker input, no object bytes are rewritten, and no assembly or binary payload enters the candidate. The diagnostic target object is used only by objdiff and symbol-order comparison.

The fragments contain the main script methods, container construction and accessors, two container copy constructors, tree accessors, and the final four tree/list accessors. Declaration-only views of selected template members suppress their definitions in the main fragment. The later fragments provide the same implementations. The allocator/root constructor ordering is obtained by a local exact-body specialization; moving the mutable list allocator declaration ahead of `size_ref` fixes their order. The main fragment retains the ten definition moves and typed distance-member address probe from F-251-3.

The pair constructor required the larger container tail, rather than a four-function fragment alone. Defining every copy constructor explicitly in the caller's header changed trivial-copy behavior and four constructor bodies. Keeping the caller's implicit copy constructors preserves those bodies. A separate fragment supplies the two genuine typed copy implementations at their required location; the native linker selects these strong definitions over the earlier weak copies. The empty `number` base is default initialized in the storage copy implementation, and the pointer member is copied. The class layouts and symbol signatures remain identical. These declaration views and explicit template specializations are D-0016 source-organization scaffolding, not recovered original source organization.

The constructor parameter types must preserve `call_traits` top-level const qualifiers even when mangling removes them: `const OneNode` and `const NodeCapacity` restore the original instruction scheduling. Explicitly declaring otherwise implicit copy constructors makes the containing type nontrivial and changes by-value argument copies, so matching a copy-constructor body alone is insufficient.

The repeatable scratch entry points are `tools/local/session/282-worldobj-buildprototype.py` and `282-worldobj-copycheck.py`. A clean five-source recompilation followed by the native join returned success for every stage and reported `240 []` for function differences and `240 240` for ordered common symbols. `joined.o` has `.text` size `0x73D8` before final dead stripping, versus the target split's `0x5488`; unused template bodies remain normal linker inputs. This is not yet full-link acceptance. The scoped source/header implementation is now present in the main checkout for parent-coordinated full SHA validation. The five source inputs are `ScriptWorldObj.cpp`, `ScriptWorldObjContainer.cpp`, `ScriptWorldObjContainerCopy.cpp`, `ScriptWorldObjTree.cpp`, and `ScriptWorldObjAccessors.cpp`; shared helper declarations live in `game/detail/ScriptWorldObjContainers.h`. Recompiling these tracked files and comparing their native join against the current real split object also reproduces all 240 bodies and their order. Full-link acceptance remains pending.

The parent integrated `partial_sources` into the ordinary build generator. The generated ninja graph compiles each of the five sources with this unit's Wii/1.1 flags and normal compiler dependency tracking, then joins only those five compiler outputs in the specified order. Independent comparison of `build/wpse-v1/src/game/ScriptWorldObj.o` against the current real `build/wpse-v1/obj/game/ScriptWorldObj.o` reports 240/240 exact function bodies and the complete 240-function target order. This confirms that the diagnostic renamed target and scratch header overlays are no longer needed to reproduce the function result.
