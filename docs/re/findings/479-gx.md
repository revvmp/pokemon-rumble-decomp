# F-479-2: GXTev, GXPixel and the retained display-list entry point

Target `wpse-v1`, original SHA-256 `ad1a59896d3ade6b2ac35c24faa578fb3cdf8c2e2d3a9040ba8784cd033053da`. Issue #479 owns thirty functions. Wii/1.0 and the existing `cflags_sdk` are used without new flags.

## Boundaries and original names

GXTev runs from 0x802CFB90 through 0x802D0260 (sixteen functions, including alignment). Its .data is 0x803D6690 through 0x803D6708: four five-word TEV operation tables followed by GXSetTevOrder's nine-entry channel lookup and trailing alignment. The compiler emits pooled `...data.0` and the original CodeWarrior local lookup name. The sixteen ordered names and sizes agree with the pinned CC0 Petari GXTev reference.

GXPixel runs from 0x802D0260 through 0x802D09E0 (thirteen functions), with .data 0x803D6708 through 0x803D6728 and .sdata2 0x804BB388 through 0x804BB3D8. GXInitFogAdjTable at 0x802D0490 is absent from this Petari source. It derives the near plane and side width from a perspective or orthographic projection, then samples ten horizontal fog correction factors using sqrt and 8-bit fractional scaling. Its implementation is independently reconstructed from the target's scalar operations and calls. GXSetFog's target writes the magnitude and exponent registers only on the perspective path; the pinned source writes them after both projection paths and needs adaptation.

Only GXCallDisplayList from GXDisplayList is retained here: .text 0x802D09E0 through 0x802D0A60, one function. The GXBeginDisplayList/GXEndDisplayList machinery and its static storage are not retained in this region. The next function at 0x802D0A60 is the projection update in GXTransform, outside this claim.

## ABI and external dependencies

The existing __GXData pointer at 0x804BB2D8 supplies GXData. The retained call-list function tests dirtyState at offset 0x5fc and the packed vNumNot/bpSentNot pair at offsets 0/2. It calls __GXSetDirtyState (0x802CCE30) and __GXSendFlushPrim (0x802CD200), both owned by #476. Those outside-range names are deliberately not edited here. GXPixel's sqrt call at 0x8034D798 also needs the owning issue's symbol integration. Existing __GXFlushTextureState at 0x802CFB60 is already named and used by GXSetFieldMode. The compiler emits __cvt_fp2unsigned calls for unsigned float conversions; its unnamed original target is 0x8034033C.

## Validation and remaining differences

The split-only configure/build completed and frozen-manifest verification exited 0. GXTev is then linked from source and the full build plus frozen-manifest verification pass. Its 1,656 non-padding code bytes are linked from reconstructed source. Source objdiff reports GXTev 16/16 exact functions, GXPixel 11/13 exact functions (99.05983 percent fuzzy; all 112 data bytes match), and GXCallDisplayList 1/1 exact functions. GXSetFog and GXInitFogAdjTable retain instruction scheduling/register allocation differences. Direct composition of the fog words using C masks changed code shape substantially and was discarded; preserve the named register helper operations when continuing this comparison.

The initial GXTev source link dropped the twelve padding bytes following GXSetNumTevStages: the original fallback GXPixel object defaulted to four-byte section alignment. Marking the observed GXSetFog entry `align:16` in symbols preserves its original boundary and restores exact artifact identity. No source padding bytes or expected hashes were fabricated.

GXPixel and GXDisplayList remain NonMatching and use original fallback objects. Their source and external dependencies are explicit; fuzzy code agreement does not establish their source link. No package, boot-executable or full-game match is claimed. No new reusable repository trap was established.

## F-479-3: Full issue completion from source

The remaining fog mismatches came from source expression lifetimes, not compiler flags. GXSetFog now constructs both perspective register words before emitting either one. This leaves the magnitude, exponent and register identifiers live in the same pattern as the original and makes all instructions exact. GXInitFogAdjTable retains `nearZ * nearZ` in its loop expression; Wii/1.0 hoists it while assigning the floating conversion constant and squared near-plane value to the original registers. These source structures agree with the CC0 ogws GXPixel reference at commit `f5a1bb5ed7692a9e09e737bc1236f592274dcf73`, `src/revolution/GX/GXPixel.c`.

The GXDisplayList split now ends at the actual GXCallDisplayList end, `0x802D0A54`, rather than the next alignment boundary, `0x802D0A60`. Its source object contains `0x74` bytes; the following automatic object owns the twelve alignment bytes. Including them in the source split shifted the following fallback functions when the source object was linked.

The outside-block sqrt entry at `0x8034D798` is named for the call used by the matching light and fog reference routines; only its name changes, with size, type and split ownership preserved. The dirty-state, primitive-flush and unsigned conversion helpers are already named on main. GXPixel and GXDisplayList can therefore link their reconstructed source without changing neighboring units.

This supersedes the remaining-difference and fallback status in F-479-2. The issue owns sixteen GXTev functions, thirteen GXPixel functions and GXCallDisplayList: all thirty are reconstructed and marked Matching. Final build and frozen-manifest validation results are recorded in the completion pull request.

## Traps

- If fog differs only in register allocation, local declaration permutations and explicit opcode writes do not fix the expression lifetimes. Construct both fog words before the writes; this reproduces the original GXSetFog instruction stream with the existing flags.
- If the fog-table conversion constant and squared near plane exchange floating registers, an explicit pre-loop square changes register allocation. Keeping the square in the loop expression lets the compiler hoist it with the original register assignment. Declaration permutations did not recover this match.
