# Issue 490: RVL_SDK dsp_task tail and NAND nand.c

## F-490-1: nand.c unit boundaries

Target `wpse-v1`, `orig/wpse-v1/main.dol` (manifest `config/targets/wpse-v1.json`). The dtk 1.8.4 split assembly `build/wpse-v1/asm/auto_03_802B1A10_text.s` shows the NAND file API from `0x802E4630` to `0x802E5BB4`, followed by alignment padding and `nandOpen` at `0x802E5BC0`, the first function of `NANDOpenClose.c` (#491). Every function in the range calls `nandIsInitialized` and `nandConvertErrorCode` or is a static helper reached only from them. The only data references are the `.sdata` strings `"/"` (`0x804B8BF0`, padded to 4 bytes) and `"/%s"` (`0x804B8BF4`), both used by `nandMove`; `__NANDVersion` at `0x804B8BF8` belongs to another NAND unit. No `.rodata`, `.data`, `.bss`, or `.sbss` is referenced. The unit therefore owns `.text` `0x802E4630`–`0x802E5BC0` and `.sdata` `0x804B8BF0`–`0x804B8BF8`. Confidence high.

## F-490-2: nand.c function set differs from Petari

Petari's CC0 `src/RVL_SDK/nand/nand.c` (commit `e0ab141`) supplies the bodies, but this game's copy links a different subset. Present here and absent from Petari: `NANDCreateAsync` (`0x802E4830`), `NANDDeleteAsync` (`0x802E4BA0`), `NANDCreateDir` (`0x802E5070`), `NANDCreateDirAsync` (`0x802E5180`), `NANDMoveAsync` (`0x802E5550`), `NANDTell` (`0x802E5660`), and `NANDGetHomeDirUsageAsync` (`0x802E5B30`). Absent here: `NANDPrivateCreateDir`, `NANDMove`, `NANDGetLengthAsync` and its helpers, `NANDSetUserData`, and `NANDGetUserData`, presumably dead-stripped. Names for the additions come from the CC0 decompilations `yomcube/cmwp-decomp` and `pbr-ret/pbr-decomp`, whose bodies they match by call pattern: privilege flag visible through the presence or absence of `nandIsPrivatePath`, async flag through `nandCallback` (`0x802E6DD0`), and `NANDTell` through the dead `stw r0, 0(r0)` store and the `offset` field load at stack `0x24`. `NANDGetHomeDirUsageAsync` passes `nandGetHomeDir()` (`0x802E71C0`, returns the home directory buffer) to the ISFS usage call at `0x802F4340`. Confidence high for the call-pattern identifications, medium for the exact original names of the additions.

`nandCreate`, `nandDelete`, `nandSeek`, `nandCreateDir`, `nandGetFileStatus`, and `nandInspectPermission` are fully inlined; `nandMove`, `nandSplitPerm`, `nandComposePerm`, `nandGetStatus`, and `nandGetStatusCallback` are emitted. `nandComposePerm` needs `__attribute__((noinline))`, as in Petari, or it is inlined into both callers. Compiled with Wii/1.0 and `cflags_sdk`, all 29 functions and 8 data bytes match in objdiff 3.8.2.

## F-490-3: nand.c cannot link from source yet

Promoting the unit to `Matching` fails to link with undefined externals whose symbols are unnamed in `config/wpse-v1/symbols.txt` and belong to other issues: `nandCallback` (`0x802E6DD0`), `nandGetHomeDir` (`0x802E71C0`), `nandGetRelativeName` (`0x802E6290`), and `nandIsUnderPrivatePath` (`0x802E64B0`) in #491; `ISFS_CreateDir` (`0x802F36E0`), `ISFS_CreateDirAsync` (`0x802F37E0`), `ISFS_GetAttr` (`0x802F3B90`), `ISFS_GetAttrAsync` (`0x802F3CF0`), `ISFS_Delete` (`0x802F3E30`), `ISFS_DeleteAsync` (`0x802F3F10`), `ISFS_Rename` (`0x802F3FE0`), `ISFS_RenameAsync` (`0x802F40F0`), `ISFS_GetUsageAsync` (`0x802F4340`), `ISFS_CreateFile` (`0x802F4470`), `ISFS_CreateFileAsync` (`0x802F4570`), `ISFS_GetFileStats` (`0x802F4800`), `ISFS_Seek` (`0x802F48D0`), `ISFS_SeekAsync` (`0x802F48E0`), `ISFS_Read` (`0x802F4970`), `ISFS_ReadAsync` (`0x802F4990`), `ISFS_Write` (`0x802F4A40`), and `ISFS_WriteAsync` (`0x802F4A60`) in #498; `strcat` (`0x80345D64`) and `strcmp` (`0x80345DDC`) in #538. The ISFS addresses follow the function order of Petari's `fs.c`, with the unlisted `ISFS_GetUsageAsync` between `ISFS_GetUsage` and `ISFS_CreateFile`. The unit stays `NonMatching` until those names land.

## F-490-4: dsp_task.c starts in the previous block

The issue's first four functions, `0x802E41C0`–`0x802E4630`, are `__DSP_exec_task`, `__DSP_boot_task` (its `__DSP_boot_task()` debug strings at `0x803DC290`), `__DSP_insert_task`, and `__DSP_remove_task`, matching the order of Petari's `dsp_task.c`. The file's first function is `__DSPHandler` at `0x802E3D90` (`0x42C` bytes), which calls `__DSP_exec_task` six times and `__DSP_remove_task` four times and uses the task list globals at `0x804B9990`–`0x804B99A4`. `__DSPHandler` lies in #489's block, so under the collaboration rules #489 owns the `dsp_task.c` split, object line, and header. These four functions were left for coordination with #489. Confidence high.

## Traps

- **Game SDK copies differ from Petari's function set.** RVL_SDK `nand.c` here links seven functions Petari lacks and omits others. Identify each function by call pattern and take names from other CC0 decompilations (`yomcube/cmwp-decomp`, `pbr-ret/pbr-decomp`), recording provenance. See F-490-2.
